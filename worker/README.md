# Admin sign-in service

The site is a static site on GitHub Pages. This Worker is the only
moving part: it checks who someone is, decides what they may change,
and commits the change to this repo. Pages rebuilds, and the site is
updated a minute or two later.

```
browser (/admin/)  ->  this Worker  ->  GitHub commit  ->  Pages rebuild
```

Nothing here is a framework and there are no dependencies.

| file            | what it does                                        |
|-----------------|-----------------------------------------------------|
| `src/index.js`  | the routes                                          |
| `src/auth.js`   | password hashing, session tokens                    |
| `src/scope.js`  | who may write what — **the security boundary**      |
| `src/github.js` | committing, via the Git Data API so a save is one commit |

Run the tests with `npm test` (33 of them, no network needed).

## Deploying it

You need a Cloudflare account and a GitHub token. Roughly 10 minutes.

### 1. Sign in to Cloudflare

```sh
wrangler login
```

### 2. Make the KV namespace that holds the logins

```sh
cd worker
wrangler kv namespace create USERS
```

It prints an id. Put it in `wrangler.toml`, replacing
`PASTE_KV_NAMESPACE_ID_HERE`.

### 3. Make a GitHub token

github.com → Settings → Developer settings → Personal access tokens →
**Fine-grained tokens** → Generate new token.

- Repository access: **Only select repositories** → `arronsnow/iloveyoutattoo`
- Permissions → Repository permissions → **Contents: Read and write**
- Nothing else. No account permissions, no other repos.

Set an expiry you will actually notice — a year is reasonable, and the
admin will start reporting save failures when it lapses.

### 4. Give the Worker its secrets

```sh
wrangler secret put GITHUB_TOKEN        # paste the token
wrangler secret put SESSION_SECRET      # any long random string
```

For the session secret, anything long and random will do:

```sh
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

These are secrets, not vars — they are never in the repo and cannot be
read back out of the dashboard.

### 5. Deploy

```sh
wrangler deploy
```

It prints a URL like `https://iloveyou-tattoo-admin.<something>.workers.dev`.

### 6. Point the site at it

Put that URL in `js/admin-config.js`:

```js
window.ILY_ADMIN_API = 'https://iloveyou-tattoo-admin.<something>.workers.dev';
```

Commit and push. Until this is set, `/admin/` on the live site shows
"The admin service is not configured for this site yet" and lets nobody
in — which is the right way round to fail.

### 7. Make the first login

There is no sign-up, by design. The first owner account is created by
hand, once:

```sh
cd worker
node scripts/make-owner.mjs jenni@example.com "Jenni"
```

It asks for the password twice and hides what you type, so it never
reaches your shell history. What goes to Cloudflare is a PBKDF2 hash and
its salt, never the password.

Run it again with a second email to create another owner — two owners
means neither can be locked out, and nobody is allowed to delete their
own login.

Then sign in at `https://iloveyou.tattoo/admin/`. Everyone else —
artists, and any second owner — Jenni creates from **Logins** inside the
admin. She should change the password you set her on first sign-in.

## What an artist can and cannot do

Enforced in `scope.js`, on the server. The admin also hides what a login
cannot reach, but that is presentation only — anyone can craft their own
request, so every write is checked again here.

An artist **can**:

- edit their own entry in `data/artists.json` — and only their own
- edit the galleries assigned to their login
- upload photos into the folders those galleries live in

An artist **cannot**:

- touch another artist's entry, or add, remove or reorder the team
- rename their own slug to claim someone else's
- change the shop details, opening hours, reviews, colours, fonts or
  home page layout
- change any HTML, CSS, JavaScript, `CNAME` or anything under `.github/`
- upload anywhere except their own photo folders

Uploaded filenames are generated by the server, never taken from the
browser, so nothing user-supplied reaches a path.

## Handing the account over to the client

The Worker is stateless code — only the logins in KV are real state.
Three options, cleanest first:

1. **Add her to this Cloudflare account** as a Super Administrator
   (Manage Account → Members), then remove yourself. No downtime.
2. **Change the account email**, which moves the whole account to her.
   Only sensible if nothing else lives in it.
3. **Redeploy into a fresh account of hers**: `wrangler deploy`, make
   the KV namespace again, re-add the logins, update
   `js/admin-config.js`. About 20 minutes.

The logins do not move by themselves in option 3 — everyone would set a
new password. Worth deciding before creating nine of them.

## If something breaks

- **"Could not reach the admin service"** — the Worker is down, or
  `ILY_ADMIN_API` is wrong. `wrangler tail` shows live logs.
- **Saves fail but sign-in works** — usually the GitHub token expired,
  or its Contents permission was dropped. `wrangler secret put
  GITHUB_TOKEN` again.
- **"Something went wrong"** — deliberately vague to the browser, so
  repo paths and GitHub responses never leak. The real error is in
  `wrangler tail`.
- **Locked out entirely** — write a fresh owner record into KV as in
  step 7. That path never depends on being able to sign in.
